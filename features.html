What Amaea actually does.

Seven systems, each grounded in a specific FCA rule. We've tried to write this the way an engineer would describe it to a compliance officer: what the product does, when it runs, what it cites.

Client journey

Three compliance stages per client: initial engagement, ad-hoc work, annual reviews. Each stage carries its own document set: 17 types in total. The system knows which are missing, which are expired, and which expire in the next 90 days.

  • 17 doc types tracked: fact find, suitability report, ATR, Consumer Duty outcome, vulnerability assessment, AML CDD, client agreement, ID&V, source-of-funds, PI cover note, T&C record, complaint log, fees disclosure, key facts illustration, drawdown review, ongoing services log, fee benchmarking
  • Expiry windows configurable per doc type; defaults match FCA file-completeness expectations
  • "Missing" vs "expired" tracked separately, so the audit-trail reason is correct when a flag is closed
  • Adviser roll-up: per-adviser breach count and missing-doc count, sortable
  • Every flag carries the specific rule citation (COBS, SYSC, FG21/1 etc.), visible on the audit log

Consumer Duty (PS22/9)

The four outcomes tracked per client per year: products & services, price & value, consumer understanding, consumer support. Vulnerability re-assessments raised automatically the day a client crosses the 12-month FG21/1 threshold.

  • Per-client outcome assessment record: one row per outcome per year, with the evidence document referenced
  • Fair-value gaps surface as risk flags with the specific PS22/9 outcome cited (not a generic "review needed")
  • FG21/1 12-month vulnerability re-assessment threshold enforced by a nightly cron
  • Board-pack export: four-outcome roll-up, vulnerable-client cohort numbers, year-on-year delta
  • If the AI helped draft an outcome justification, the audit trail records prompt + response SHA-256s

Annual review sweep

A nightly cron evaluates every overdue review against COBS 9.5. If no reason is recorded, a flag is raised. If a reason is recorded, an FCA-trained AI assesses it against the rule's actual sufficiency test (bereavement, illness, documented unavailability) and either resolves the flag or escalates it, with the reasoning written to the audit log.

  • Runs nightly · idempotent · cursor-paginated so it resumes cleanly if a run is interrupted
  • COBS 9.5 sufficiency test, not a date-based rule: "the review was delayed because the client was abroad for three months" passes; "we forgot" doesn't
  • Every AI decision attaches prompt SHA-256, response SHA-256, model version, and timestamp to the flag's audit trail
  • Flag escalations follow the firm's configured escalation matrix; no email goes out without an assignee
  • Special-category client data (Article 9 UK GDPR) is held in-process: never logged, never sent to the LLM in the clear

AI assistant with hash-verifiable audit trail

Claude Sonnet 4.6 retrieval-grounded against your firm's records + an 11,645-chunk FCA Handbook corpus. Every response writes prompt + response SHA-256s, model version, and request ID to the audit log: the same record the FCA would read if they queried what the model actually said on the day.

  • Retrieval first, generation second. The model is told to cite from the corpus or refuse; "I don't have a confident answer" is a first-class response, not an error state
  • Per-firm vector isolation. pgvector table protected by RLS; the database refuses cross-firm reads, not application code
  • Article 9 redaction. Vulnerability, health, and ethnicity fields are redacted before the prompt is built; the LLM never sees the raw values
  • Zero training. Anthropic API is called per request only; Zero Data Retention in progress with the vendor
  • 50-scenario eval suite runs against every model release; the current best is documented internally before cutover
  • Disclaimer on every surface rendering AI output: decision support, not regulated advice

RMAR auto-population

Sections B, D, E, G, and H pre-filled from your live data. Each section exports as a CSV ready for GABRIEL upload. The first time you run it, expect to spend an afternoon reconciling discrepancies; from the next quarter onwards, the same run takes under an hour.

  • Section B: complaints, drawn from the complaint log and cross-checked against DISP 1.6 (FOS rights communicated, 5-day acknowledgement, 8-week final response)
  • Section D: financial resources, pulled from the firm's connected platform feed
  • Section E: PII renewal status, pulled from the policy schedule you upload at renewal
  • Section G: adviser roster, pulled from the live roster table; only currently-active advisers counted
  • Section H: training records, drawn from the T&C record set against each adviser

Amaea Horizon

FCA publications, indexed the day they ship.

Our retrieval corpus already holds 11,645 chunks across 150 sources: the Handbook, Final Notices, Dear CEO letters, Policy Statements, Thematic Reviews. New publications are ingested on a daily cron. The personalised "what this means for your firm" layer is on the public-launch roadmap and not yet shipped; the corpus itself is live and queryable inside the AI assistant today.

  • Daily ingest of FCA publications: chunked, embedded with Voyage AI, written to a per-firm-isolated pgvector table
  • Every chunk carries source, publication date, and section reference; citations the AI returns are clickable through to the original PDF
  • Roadmap: per-firm impact analysis ("does this affect your client book?"), targeted for the Q1-2028 release
  • If the AI can't find a confident answer in the corpus, it says so explicitly. No fabricated rule citations
  • Continuous evaluation suite (50 FCA-scenario gold set) runs against every model release before we cut over

Integrations

OAuth-authenticated. Tokens encrypted with AES-256-GCM at the application layer; the encryption key sits in a Vercel environment variable, not in the database. Sync is nightly by default; on-demand pull available per integration.

  • Intelliflo: client records, review dates, valuations; nightly delta sync
  • SharePoint: document pull; new files routed to the correct client via filename heuristic + confirmation prompt
  • Salesforce, Curo, Assureweb: same OAuth + encrypted-token pattern; available on request
  • Dynamic Planner, ThreeSixty, Evidentli, DocuSign: REST-based, scoped tokens, read-only by default
  • If you're on a platform that exposes documents over OAuth or REST, we can integrate it. Tell us what you use and we'll tell you whether it's a week's work or three
